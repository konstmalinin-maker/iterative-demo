# Аналитическая записка: сравнение моделей жизненного цикла ПО

## 1. Цель исследования

Цель практической работы — исследовать, как организация разработки и стратегия фиксации изменений влияют на читаемость истории Git, восстановление контекста изменений, откат отдельных изменений и поиск ошибок.

Для сравнения созданы два публичных учебных репозитория с консольным калькулятором на Python. Оба проекта предусматривают сложение, вычитание, умножение, деление с обработкой деления на ноль, интерфейс командной строки и автоматические тесты:

- **[waterfall-demo](https://github.com/konstmalinin-maker/waterfall-demo)** — учебная имитация каскадной разработки: исходный код, тесты и документация добавлены одним коммитом `ac853ce` после завершения проекта.
- **[iterative-demo](https://github.com/konstmalinin-maker/iterative-demo)** — учебная имитация итеративно-инкрементальной разработки: функциональность добавлялась последовательными коммитами с осмысленными сообщениями. Для исходного сравнения использованы девять коммитов, заканчивающиеся коммитом `c60de4d`.

В дальнейшем в `iterative-demo` выполнялись дополнительные задания, поэтому количественные показатели рассчитаны по **исходным девяти коммитам**, а не по всей более поздней истории репозитория.

## 2. Сравнение метрик

| Метрика | Waterfall | Iterative |
|---|---:|---:|
| Количество исходных коммитов | 1 | 9 |
| Количество файлов в исходной версии | 7 | 7 |
| Всего добавлено строк | 167 | 174 |
| Всего удалено строк | 0 | 17 |
| Общий объём изменений (добавления и удаления) | 167 строк | 191 строка |
| Среднее число добавленных строк на коммит | 167 | 19,3 |
| Средний объём изменений на коммит | 167 строк | 21,2 строки |
| Среднее количество изменённых файлов на коммит | 7 | 1,78 |
| Характер сообщений | Одно общее сообщение | Сообщения по Conventional Commits |
| Стратегия фиксации изменений | Один коммит для всего проекта | Отдельные коммиты для этапов и функций |

Для `waterfall-demo` использованы результаты `git log --stat` и `git rev-list --count HEAD`. Для `iterative-demo` данные получены из `git log --shortstat --oneline c60de4d` и `git ls-tree -r --name-only c60de4d`. Суммарно в девяти исходных коммитах Iterative изменено 16 файловых позиций: один и тот же файл учитывается повторно, если он изменялся в нескольких коммитах.

Первоначально оба проекта содержат одинаковое число файлов. Различие проявляется прежде всего в истории: в Waterfall все 167 строк добавлены одним коммитом, а в Iterative 191 операция добавления или удаления распределена между девятью этапами. Больший суммарный объём изменений в Iterative связан в том числе с последовательным дополнением и исправлением ранее созданных файлов.

## 3. Результаты экспериментов

### 3.1. Восстановление контекста изменений

**Цель:** выяснить, насколько удобно определить, когда и зачем была реализована функция `divide`.

В `waterfall-demo` команда `git log -S "def divide" --oneline -- src/calculator.py` указывает на единственный коммит `ac853ce` (`Initial commit: full calculator implementation`). В этом коммите одновременно находятся все арифметические операции, интерфейс, тесты и документация. Чтобы изучить появление функции деления, приходится просматривать общий патч.

В `iterative-demo` та же команда находит отдельный коммит `870a1aa` — `feat(calculator): implement divide with zero-division handling`. Команда `git show 870a1aa -- src/calculator.py` позволяет изучить соответствующие изменения без просмотра всего проекта.

**Вывод:** поэтапная история с информативными сообщениями помогает быстрее восстановить назначение изменения. Точное время поиска в ходе эксперимента не замерялось, поэтому количественное сравнение скорости не приводится.

### 3.2. Откат конкретного изменения

**Цель:** сравнить возможность отмены реализации умножения без отмены всего проекта.

В `waterfall-demo` отдельного коммита с реализацией `multiply` нет: весь проект добавлен одним коммитом. Отмена этого коммита через `git revert HEAD` затронула бы всю первоначальную реализацию. Чтобы удалить только умножение, пришлось бы вручную изменить исходный код и соответствующие тесты.

В `iterative-demo` был выбран коммит `497a81c`, связанный с реализацией умножения. Попытка выполнить `git revert --no-edit 497a81c` в экспериментальной ветке на основе актуальной истории привела к конфликтам в `src/calculator.py` и `tests/test_calculator.py`, поскольку после этого коммита файлы продолжали изменяться.

После отмены незавершённого отката была создана ветка непосредственно от коммита `497a81c`. В ней `git revert --no-edit HEAD` завершился успешно и создал коммит отката `9e9dc19`. Откат изменил два файла: три строки были добавлены и двенадцать удалены. При этом отменяемый коммит содержал также изменения, затрагивающие вычитание, поэтому результат нельзя считать изолированной отменой только функции умножения.

**Вывод:** отдельные коммиты позволяют выбирать изменения для отката, но поздние зависимости могут вызвать конфликты. Для действительно адресного отката важна не только небольшая величина коммита, но и его логическая атомарность.

### 3.3. Анализ авторства строк с помощью `git blame`

**Цель:** определить, к каким этапам разработки относятся отдельные строки исходного кода.

В `waterfall-demo` команда `git blame src/calculator.py` связывает все строки исходного файла с первоначальным коммитом `ac853ce`. По такой истории нельзя определить порядок реализации отдельных функций.

В исходной истории `iterative-demo` строки распределены между разными коммитами. Например, реализация сложения связана с `9f08e99`, а функция деления — с `870a1aa`. При этом `git blame` показывает последний коммит, затронувший конкретную строку: если код меняли позднее, он может отображать более новый коммит, а не первоначальный момент создания функции.

**Вывод:** поэтапная история помогает проследить происхождение отдельных строк, хотя результаты `git blame` необходимо интерпретировать вместе с `git log` и `git show`.

### 3.4. Поиск регрессии с помощью `git bisect`

**Цель:** найти коммит, после которого перестал проходить тест умножения.

Для эксперимента создана отдельная ветка `experiment/bisect`. После рабочего коммита с документацией в функцию `multiply` намеренно внесена ошибка: вместо `return a * b` записано `return a + b`. Затем были сделаны дополнительные коммиты, не исправляющие ошибку.

С помощью `git bisect start`, `git bisect bad HEAD` и `git bisect good main` заданы границы поиска. Во время проверки Git переключился на коммит `bcc42b3` (`test: simulate multiplication regression`). Запуск pytest на этом коммите дал результат: **четыре теста прошли, один тест `test_multiply` не прошёл**. При проверке `multiply(3, 4)` программа вернула `7` вместо ожидаемых `12`. Именно в коммите `bcc42b3` была сделана намеренная ошибочная замена.

**Вывод:** `git bisect` позволяет сузить область поиска регрессии, проверяя промежуточные версии. В данном эксперименте он помог локализовать ошибку, связанную с функцией умножения.

### 3.5. Дополнительное сравнение файлов через `diff`

После выполнения основных этапов оба репозитория были клонированы в отдельные каталоги и сравнены командой `diff -rq` с исключением служебных директорий. В момент сравнения папка `docs` имелась только в `iterative-demo`; также различались `README.md`, `src/calculator.py`, `src/cli.py` и `tests/test_calculator.py`.

Подробное сравнение исходного кода выявило улучшенное сообщение об ошибке деления на ноль в `iterative-demo`. Кроме того, в проверенной версии этого репозитория оставалось повторное определение функции `subtract` со старой заглушкой `NotImplementedError`. Повторное определение не мешало выполнению последующей рабочей версии функции, но указывало на необходимость очистки кода.

Часть различий вызвана выполнением дополнительных заданий и последующими исправлениями, а не самим выбором модели жизненного цикла. Поэтому структуру файлов нельзя использовать как самостоятельное доказательство преимуществ одной из стратегий.

## 4. Выводы

1. В учебной имитации Waterfall история из одного большого коммита не раскрывает последовательность реализации функций. Для поиска конкретного изменения требуется изучать общий патч.
2. В учебной имитации Iterative девять исходных коммитов дают более подробную картину разработки: функции, интерфейс, документация и исправления отражены отдельными сообщениями.
3. Итеративная история упрощает выбор коммита для анализа и отката, но сама по себе не предотвращает конфликты и не гарантирует идеальную атомарность. Это подтвердил эксперимент с откатом коммита умножения.
4. `git blame` позволяет связывать строки с историей изменений, а `git bisect` — находить регрессии с помощью последовательных проверок промежуточных версий.
5. Различия файловых структур после дополнительных заданий нельзя автоматически объяснять различиями моделей жизненного цикла: на них также влияют дальнейшие изменения, исправления и оформление проекта.

Представленные результаты характеризуют прежде всего **две учебные стратегии ведения Git-истории**. Реальная каскадная модель не требует одного коммита, а итеративная модель сама по себе не гарантирует качественную историю: в работе эти стратегии намеренно противопоставлены для наглядного эксперимента.

## 5. Рекомендации

Для проектов, которые развиваются длительное время или сопровождаются несколькими разработчиками, рекомендуется фиксировать логически завершённые изменения отдельными коммитами с понятными сообщениями, например по соглашению Conventional Commits. При этом каждый коммит желательно проверять тестами и не объединять в нём несвязанные задачи.

В проектах с каскадным планированием также полезно регулярно фиксировать завершённые изменения в Git, даже если выпуск результата организован по крупным этапам. Для небольших одноразовых проектов история может быть короче, но сообщения должны оставаться понятными.

При исследовании ошибок следует сочетать `git log`, `git show`, `git diff`, `git blame` и `git bisect`. Перед рискованными операциями `git revert`, `git reset` и `git rebase` желательно создавать отдельную ветку и сохранять нужные результаты для отчёта.
