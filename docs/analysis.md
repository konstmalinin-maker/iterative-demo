# Аналитическая записка: сравнение моделей жизненного цикла ПО

## 1. Цель исследования

Цель работы — сравнить влияние двух стратегий разработки на историю Git, поиск изменений, откат коммитов и поиск ошибок.

В рамках работы созданы два учебных репозитория с консольным калькулятором на Python: waterfall-demo и iterative-demo. В первом весь проект был зафиксирован одним коммитом, во втором функциональность добавлялась поэтапно.

## 2. Сравнение метрик

| Метрика | Waterfall | Iterative |
|---|---:|---:|
| Первоначальное количество коммитов | 1 | 9 |
| Файлов в первоначальной версии | 7 | Уточнить |
| Добавлено строк | 167 | Уточнить |
| Средний размер коммита | 167 добавленных строк | Уточнить |
| Стратегия | Один общий коммит | Поэтапные функциональные коммиты |

## 3. Результаты экспериментов

### 3.1. Восстановление контекста

В waterfall-demo функция divide появилась в единственном коммите ac853ce, содержащем весь проект. В iterative-demo добавление деления связано с отдельным коммитом 870a1aa. Его сообщение позволяет определить назначение изменения без просмотра всей истории проекта.

### 3.2. Откат изменений

В Waterfall отмена единственного первоначального коммита затрагивает весь проект. В Iterative можно выбрать коммит, связанный с конкретной функциональностью.

Попытка отменить коммит 497a81c в актуальной версии iterative-demo привела к конфликтам в calculator.py и test_calculator.py. При создании отдельной ветки непосредственно от исторического коммита откат прошёл успешно. При этом он затронул и дополнительные изменения, попавшие в исходный коммит.

### 3.3. Git blame

В waterfall-demo все строки калькулятора связаны с первоначальным коммитом. В iterative-demo строки относятся к различным этапам разработки, поэтому можно восстановить контекст появления отдельных операций.

### 3.4. Git bisect

Для эксперимента в отдельной ветке была создана регрессия: функция multiply вместо умножения выполняла сложение. На коммите bcc42b3 тест обнаружил ошибку: фактический результат составил 7 вместо ожидаемых 12. Остальные четыре теста прошли.

Использование git bisect позволило проверить промежуточные состояния репозитория методом бинарного поиска.

## 4. Выводы

Поэтапное сохранение функциональности отдельными коммитами облегчает поиск причин изменений, изучение истории и выбор конкретных изменений для отката. При этом последующие зависимости могут осложнить отмену старых коммитов.

Стратегия одного большого коммита не позволяет восстановить внутреннюю последовательность разработки. В данном эксперименте это затруднило анализ отдельных функций.

## 5. Рекомендации

Для проектов с длительным сопровождением и командной разработкой целесообразно сохранять логически завершённые изменения отдельными информативными коммитами. При небольшом объёме работы структура истории может быть проще.

Следует учитывать, что реальная каскадная модель разработки не обязательно предполагает один коммит: в этой работе такая стратегия использовалась специально для учебного сравнения.
